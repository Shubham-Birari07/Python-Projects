Station 01

Why Pydantic Exists

Programs assume the data they receive is well-formed. In reality, data arrives from files, forms, other systems, and people — and it is rarely perfect. Pydantic's entire job is to stand at that entry point and refuse to let anything through that doesn't match what your program expects, before it causes a confusing failure somewhere else.

Station 03

Field Rules & Constraints

Beyond just "what type is this," you can attach specific rules to a single piece of information — a minimum length, a number range, an exact pattern it must match. You can also attach a plain description, so anyone reading the form later understands what each field means.

Tap a rule category to see an example

Length Rules

A name field might require at least 2 characters and no more than 50. Too short, and the checkpoint assumes it's a typo or placeholder; too long, and something has probably gone wrong upstream.

Range Rules

A price field can require a value greater than zero. An age field might require a value between 0 and 120. Anything outside the range is turned away immediately, no further questions asked.

Pattern Rules

Some fields must follow an exact structure — like a postal code, a product code, or a phone number. A pattern rule checks the data is shaped correctly, even if every individual character is technically valid.

Description & Metadata

You can attach a short note to any field explaining what it means or how it should be used. This doesn't change what's accepted — it simply makes the form self-explanatory for whoever reads it next.

Custom Validators

Sometimes a type or constraint isn't enough — you need a rule that reasons like a person would, such as "the discount price must be lower than the original price." Validators let you write that logic, and they come in two scopes: checking one field alone, or checking the whole form together.

Station 08

Aliases & Computed Fields

An alias lets a field go by a different name on the outside than the one you use internally — useful when external data follows a different naming style. A computed field never receives a value at all; it's worked out automatically from the other fields.

Alias
Tap to reveal

The outside world sends a field under one name; internally your program refers to it by a different, more consistent name. Pydantic quietly maps one to the other.

Station 09

Special Data Types

Beyond plain text and numbers, Pydantic already understands many real-world formats out of the box, and double-checks they're properly shaped, not just present. It can also describe your entire model as a formal blueprint that other tools and teams can read.

Tap a scanner to see what it checks
Email Scanner
Confirms the text is actually shaped like a real email address — not just any string with letters in it.
Web Link Scanner
Confirms a value is a properly structured web address, not just text that happens to contain dots and slashes.
ID Chip Scanner
Confirms a value is a properly formatted unique identifier, used to tell records apart without any chance of collision.
Exact Decimal Scale
Confirms a number keeps exact precision — critical for money, where rounding errors are never acceptable.
Date Stamp Scanner
Confirms a date or time value is real and properly formatted — no 32nd of the month getting through.
Station 10

Settings Per Environment

The same program often needs to behave differently depending on where it's running — a developer's laptop versus a live server used by real customers. Settings management lets a program read its configuration automatically from wherever it happens to be running, instead of having values hardcoded.

Station 11

Reading Validation Errors

When data fails the checkpoint, Pydantic doesn't just say no — it hands back a detailed report naming exactly which field failed and why. Learning to read this report quickly is one of the most useful everyday skills when working with Pydantic.
